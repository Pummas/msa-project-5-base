## Контекст

Для локального POC требуется регулярно запускать batch ETL: проверять готовность входных данных, выполнять
последовательные шаги обработки, сохранять результаты и уведомлять о проблемах. Ориентир — до 1 млн записей за запуск,
но сам оркестратор не должен обрабатывать этот объём: Airflow только планирует, связывает и контролирует внешние задачи,
хранилища и вычислительные engines.

Исходный набор проекта не содержал готовых Airflow-артефактов. Локальное решение должно запускаться в Docker Compose, а
затем переноситься в облако без изменения бизнес-логики обработки.

Ключевые требования:

| Требование       | Ожидаемое покрытие                                                                                                                                                         |
|------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Функциональные   | Расписание и зависимости; интеграции с файлами, PostgreSQL, BigQuery, Redshift, Kafka и Spark; последовательные и условные задачи; event triggers; retry/fallback и email. |
| Нефункциональные | Наблюдаемость, повторный запуск, идемпотентность, локальный POC в Docker Compose и перенос в managed/cloud-среду.                                                          |

## Рассмотренные варианты

### Вариант №1 «Apache Airflow»

Airflow — оркестратор DAG с последовательными и условными задачами. Он предоставляет расписание, зависимости, branching,
наблюдаемость и историю запусков.

Интеграции подключаются через готовые расширения и подключения: файлы и PostgreSQL — напрямую, BigQuery/Redshift/Kafka —
через соответствующие integrations, Spark — запуском внешних jobs через `SparkSubmitOperator` или `SparkSqlOperator`.
Event triggers могут быть реализованы через Datasets, sensors или внешний API-trigger. Retry задаётся политикой задач,
email — средствами уведомлений, а fallback — явно спроектированной альтернативной веткой с подходящими `trigger_rule`;
`trigger_rule` сам по себе не является event trigger.

Локально Airflow предлагается развернуть через Docker Compose с PostgreSQL для metadata и локальными файлами. В облаке
возможны managed Airflow или Kubernetes, объектное хранилище, управляемая metadata database, cloud secrets и
масштабируемые executors.

### Вариант №2 «Kubernetes CronJobs»

Kubernetes CronJobs запускают регулярные независимые задачи в контейнерах. Они подходят для простых периодических
batch-процессов, но зависимости, branching, единая история workflow и сложный fallback потребуют дополнительных средств.

Интеграции, обработка данных, retry и email/fallback в основном реализуются внутри приложений или
Kubernetes-инфраструктуры. Вариант естественен для облачного Kubernetes, но для локального POC требует локального
Kubernetes вместо более простого Docker Compose.

### Вариант №3 «Spring Batch + Spring Cloud Data Flow»

Spring Batch предназначен для цепочек взаимосвязанных batch-шагов с контролем состояния, checkpoint и продолжением после
сбоя. Spring Cloud Data Flow добавляет запуск и мониторинг таких приложений.

Вариант подходит для Java/Spring-ландшафта и может масштабироваться в соответствующей инфраструктуре. Однако для данного
POC потребуется больше специализированных Spring-компонентов для интеграций, event triggers, условных переходов и
уведомлений.

## Сравнение альтернатив

| Вариант решения                                    | Преимущества                                                                                                                                                                      | Недостатки                                                                                                                                                      |
|----------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Вариант №1 «Apache Airflow»                        | - DAG с последовательными и условными задачами<br>- Готовые интеграции и наблюдаемость<br>- Retry, явный fallback, event triggers и email<br>- Docker Compose и облачные варианты | - Требует metadata database и инфраструктурных компонентов<br>- Не заменяет обработчик данных, хранилище или вычислительный engine                              |
| Вариант №2 «Kubernetes CronJobs»                   | - Простые регулярные независимые задачи<br>- Нативная работа в Kubernetes<br>- Изоляция контейнеров                                                                               | - Нет полноценной модели DAG<br>- Зависимости, branching, fallback и уведомления требуют дополнительной реализации<br>- Менее удобен для локального Compose POC |
| Вариант №3 «Spring Batch + Spring Cloud Data Flow» | - Цепочки взаимосвязанных batch-шагов<br>- Контроль состояния и восстановление jobs<br>- Подходит для Java/Spring-систем                                                          | - Требует Spring-приложений и инфраструктуры<br>- Интеграции и event triggers собираются из нескольких компонентов<br>- Сильнее привязан к Java/Spring          |

## Принятое решение

Принят вариант №1 «Apache Airflow» как оркестратор пакетной обработки для локального POC.

Airflow лучше соответствует требованиям благодаря DAG-модели, последовательным и условным задачам, готовым интеграциям,
event triggers, retry, явно спроектированным fallback-веткам с `trigger_rule`, email-уведомлениям и наблюдаемости.
Обработку до 1 млн записей выполняют внешние SQL/Python/Spark/warehouse-задачи; Airflow только оркестрирует их.

Локальная схема — Docker Compose с Airflow, PostgreSQL metadata database и локальными файлами. При переносе в облако
используются managed Airflow или Kubernetes, объектное хранилище, управляемая metadata database, секреты облачной
платформы и масштабируемые executors.

Риски и ограничения: не определены SLA, рост объёма, retention, RPO/RTO и production-политики безопасности; локальный
POC не проверяет отказоустойчивость. Повторяемые задачи должны быть идемпотентными, а event triggers, fallback и канал
уведомлений требуют явной настройки. Airflow добавляет инфраструктурную и операционную сложность и не заменяет
streaming-платформу, хранилище или distributed compute engine.
