# ADR-04: Асинхронная загрузка номенклатуры на Spring Batch

## Общая информация

1. **Родительский артефакт** — архитектурное описание TradeWare; To Be: [`schemas/task4-context.puml`](schemas/task4-context.puml).
2. **Автор ADR** — Лукин М.А.
3. **Статус** — На согласовании.
4. **Согласующие** — команда TradeWare, владелец складского процесса, эксплуатация/DevOps.

## Контекст

Сейчас ETL выполняется в монолите и может занимать API-потоки и ресурсы онлайн-контура. Нужна постепенная миграция загрузки CSV в отдельный компонент с повторным запуском после сбоя и сохранением состояния обработки.

Входные CSV хранятся в GCS. Batch должен читать файл и справочные данные, валидировать и преобразовывать строки, затем обновлять PostgreSQL с номенклатурой. Требуются история запусков, checkpoint/restart, retry/skip и базовая наблюдаемость: логи, метрики и алерты.

Инженерная команда уже разрабатывает на Java 11 и использует WildFly. Поэтому Java-решение снижает порог внедрения и позволяет постепенно выносить ETL из монолита без смены основного стека. Spring Batch выбран не только из-за опыта отдельных сотрудников, но и благодаря готовым batch-возможностям: job/step, chunk-обработке, checkpoint, retry/skip и `JobRepository`.

## Рассмотренные варианты

### Вариант №1 «Spring Batch в отдельном batch-worker с встроенным расписанием»

Отдельное Spring-приложение на Java 11 выполняет job с шагами чтения CSV из GCS, чтения справочников из PostgreSQL, обработки и записи номенклатуры в PostgreSQL. В том же приложении расписание реализуется средствами Spring Scheduling (`@Scheduled`), а Spring Batch отвечает за выполнение job. `JobRepository` хранит состояние job/step, параметры и checkpoint, чтобы job можно было безопасно продолжить или повторить.

Spring Batch сам не является scheduler: расписание реализуется внутри того же Spring-приложения средствами Spring Scheduling. API монолита регистрирует операцию и передаёт запрос на запуск. Логи, метрики и ошибки отправляются в систему наблюдаемости (ELK, Prometheus/Grafana и алерты).

### Вариант №2 «Kubernetes Job/CronJob и собственная обработка»

Kubernetes предоставляет запуск, расписание и жизненный цикл контейнера, но чтение CSV, chunk/checkpoint, retry/skip, историю job и обработку бизнес-ошибок придётся реализовать самостоятельно.

### Вариант №3 «Apache Airflow»

Airflow хорошо подходит для расписаний и DAG-зависимостей, но добавляет отдельную платформу. Саму обработку CSV и сохранение состояния ETL всё равно придётся реализовать в приложении.

### Вариант №4 «Spring Cloud Data Flow + Spring Batch»

SCDF предоставляет управление Spring-задачами и потоками, но для одного контура добавляет server/launcher и эксплуатационные зависимости, которые сейчас не нужны.

### Вариант №5 «Синхронная обработка в монолите»

Минимум новых компонентов, но длительная загрузка блокирует API, конкурирует с онлайн-операциями и сложнее возобновляется после сбоя.

## Сравнение альтернатив

| Вариант решения | Преимущества | Недостатки |
|---|---|---|
| Spring Batch в отдельном worker | Подходит Java 11/WildFly; готовые job/step, checkpoint, retry/skip и `JobRepository`; постепенный вынос ETL | Нужны отдельный worker, встроенное расписание и настройка интеграции с GCS/наблюдаемостью |
| Kubernetes Job/CronJob | Простое расписание и изоляция контейнера | Batch-состояние, checkpoint и бизнес-обработка реализуются самостоятельно |
| Apache Airflow | Зрелые расписания, DAG, retry и уведомления | Избыточная платформа; ETL-логику и checkpoint всё равно нужно писать |
| Spring Cloud Data Flow + Spring Batch | Управление Spring-задачами и потоками | Избыточен для одного ETL-контура, больше компонентов |
| Синхронный монолит | Мало изменений и компонентов | Блокирует API, ухудшает SLA онлайн-функций, сложнее restart/retry |

## Принятое решение

Принят **вариант №1 «Spring Batch в отдельном batch-worker с встроенным расписанием»**.

Расписание реализуется внутри того же Spring-приложения средствами Spring Scheduling (`@Scheduled`), а Spring Batch отвечает за выполнение job. API монолита регистрирует операцию и передаёт запрос на запуск, не выполняя тяжёлую загрузку в пользовательском запросе. Worker читает входной CSV из GCS и справочные данные из PostgreSQL, а затем обновляет PostgreSQL с номенклатурой. `JobRepository` хранит состояние job/step и checkpoint.

Решение соответствует уже используемым Java 11 и WildFly, снижает порог внедрения и поддерживает постепенный вынос ETL из монолита. Для эксплуатации настраиваются логи, метрики длительности/ошибок и алерты.

## Последствия и ограничения

- Появляется отдельное Spring-приложение batch-worker; его расписание, deployment и лимиты нужно настроить.
- При нескольких репликах нужен distributed lock или leader election, чтобы job не запускался дублированно.
- GCS reader, идемпотентность, правила retry/skip и атомарное обновление номенклатуры требуют явной реализации.
- `JobRepository` следует размещать в PostgreSQL и определить retention истории запусков.
- Система наблюдаемости должна собирать логи, метрики и оповещения о сбоях и задержках.
- Производительность и допустимое число параллельных запусков проверяются нагрузочными тестами; Spring Batch сам по себе не обеспечивает их масштабирование.
